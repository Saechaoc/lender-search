<objective>
Append a separate `--custom` migration `0001_force_rls.sql` containing the `ALTER TABLE ... FORCE ROW LEVEL SECURITY` clauses for both `tenant` and `_rls_canary`, then [BLOCKING] apply all Phase 1 migrations (`0000_initial.sql` + `0001_force_rls.sql`) against the docker postgres container via `pnpm drizzle-kit migrate`. After this plan, RLS is FORCED on every tenant-scoped table — the table owner (the migration role) is subject to the policy, closing the Pitfall 2 gap that Drizzle 0.45's schema API does not model FORCE.

Purpose: TNT-01's structural completion. Without this plan, RLS is enabled but the table owner bypasses it silently — pen tests connecting as a non-owner pass vacuously while admin scripts running as owner exfiltrate data. The separate migration file is non-negotiable: hand-editing `0000_initial.sql` to add FORCE means the next `drizzle-kit generate` overwrites it (Pitfall 2 + RESEARCH §Pattern 2). The `--custom` migration is append-only and survives schema regeneration.

Output: `db/migrations/0001_force_rls.sql` (hand-authored, two ALTER statements). All migrations applied to the live docker Postgres 16. `pg_class.relforcerowsecurity` returns `t` for both tables (verified by direct psql introspection).
</objective>
