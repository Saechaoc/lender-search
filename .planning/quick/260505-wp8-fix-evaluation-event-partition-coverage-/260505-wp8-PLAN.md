<objective>
Fix the evaluation_event partition coverage time-bomb flagged in code review P2.b. Migration 0008 only inline-creates partitions for May-Oct 2026 and the cron function only ever creates the *next* month — so:
- After 2026-10-31, a fresh DB has no partition matching `now()` and `INSERT ... DEFAULT now()` raises `no partition of relation "evaluation_event" found for row`.
- Local Docker has no pg_cron (0009 swallows the EXCEPTION) — partitions never auto-create on local dev once the inline window expires.
- Even with pg_cron live, a migration applied mid-month leaves the rest of the migration month unprotected (cron only fires `0 2 1 * *`).

Per the migration-immutability convention (CLAUDE.md), we ship a NEW migration 0016 instead of editing 0008. The fix:
- Inline-creates the current calendar month partition + 6 forward partitions (idempotent: `CREATE TABLE IF NOT EXISTS`).
- `CREATE OR REPLACE`s `create_next_evaluation_event_partition()` so it ensures BOTH current and next month exist (so a mid-month migration application never leaves a coverage gap, and the cron path remains correct).
- Mirrors 0008's RLS+FORCE+tenant_isolation policy + REVOKE UPDATE,DELETE + GRANT SELECT,INSERT pattern on every new child (Pitfall PG-1: RLS does not auto-propagate to children in PG16; Pitfall PG-2: defense-in-depth REVOKE).

Purpose: closes the AUD-01..03 correctness regression before any audit-log call sites land in Phase 4+. Without this fix, INSERTs to evaluation_event will silently start failing in production after 2026-10-31.
Output: 1 new migration file + journal entry + 1 new test file + 2 existing tests updated to accommodate the wider partition window.
